# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

This is the **dnSpy MCP extension** — a standalone git repo that is cloned *into* a [dnSpyEx](https://github.com/dnSpyEx/dnSpy) checkout at `Extensions/dnSpy.Extension.MCP/`. It is a dnSpy extension (MEF-loaded `*.x.dll`) that runs an HTTP server inside the dnSpy process and exposes 32 assembly-loading / analysis / decompilation / IL-editing / metadata-renaming / string-search / cross-reference / codegen tools and 6 embedded BepInEx docs to AI assistants over Model Context Protocol (JSON-RPC 2.0) — over HTTP from inside dnSpy, or over stdio without the dnSpy window through the headless host in `headless/`.

## Build

**Prerequisite: a dnSpyEx checkout with submodules initialized.** The csproj has two `ProjectReference`s (`../../dnSpy/dnSpy.Contracts.DnSpy/` and `../../dnSpy/dnSpy.Contracts.Logic/`) and imports `../../DnSpyCommon.props`. Without the parent checkout and `git submodule update --init --recursive` in it, restore fails.

Target frameworks are inherited from `../../DnSpyCommon.props` (currently `net48;net10.0-windows`). Don't pin TFMs in this csproj — let the common props drive it.

```bash
dotnet build -c Release                     # both TFMs (~3s; only the two Contracts refs)
dotnet build -c Debug -f net48              # single-TFM iteration
dotnet build -c Debug -f net10.0-windows
dotnet build headless -c Release            # the headless host, both TFMs (builds the extension too)
```

Output: `bin/<Config>/<TFM>/dnSpy.Extension.MCP.x.dll`. The **`.x` suffix is mandatory** — dnSpy's extension loader skips files without it. Deploy by copying the DLL into `<dnSpy-Install>\bin\Extensions\dnSpy.Extension.MCP\` — the folder name must match the DLL stem. Placing the DLL one level up under `bin\Extensions\` silently fails.

There is no unit-test suite; the end-to-end suite is `tests/fixtures/run-tests.ps1` (see Test fixture below). CI (`.github/workflows/build.yml`) runs `tests/check-host-deps.ps1` and builds both TFMs. `release.yml` runs when a GitHub Release is **published** — pushing a `v*.*.*` tag alone does not trigger it — then runs the same guard and the parent repo's `build.ps1`, stamps the tag (minus its `v`) into the extension as `McpExtensionVersion` (what clients see as `serverInfo.version`; every other build reports `0.0.0-dev`), and attaches all-in-one zips.

**We build against a pinned dnSpyEx tag, never master.** Both workflows set `DNSPY_REF` (currently `v6.6.0`) and pass it as the checkout `ref`. This is load-bearing for two reasons: the all-in-one zips *bundle* that dnSpy build, so tracking master would ship users an unreleased snapshot; and the standalone extension DLL gets dropped into whatever dnSpy the user installed — the official release — whose net48 NuGet versions our own pins must match exactly (see the net48 binding note under Conventions). Building against master made that target move day to day, which is how issue #21 shipped. To adopt a newer dnSpy: bump `DNSPY_REF` in **both** workflows, check out that tag locally (`git -C ../../ checkout <tag> && git submodule update --init --recursive`), run `tests/check-host-deps.ps1`, and update whatever net48 `PackageReference` it flags. Keep local checkouts on the pinned tag — the guard warns when they drift, because otherwise its version comparison describes your checkout rather than what we ship.

## Architecture

- **`TheExtension.cs`** — `[ExportExtension]` MEF entry. Starts the server on `ExtensionEvent.Loaded` (if enabled), stops it on `AppExit`.
- **`McpServer.cs`** — single `HttpListener` on **both TFMs**. Kestrel was intentionally dropped: dnSpy's self-contained .NET bundle does not include ASP.NET Core, so referencing `Microsoft.AspNetCore.*` causes a silent `TypeLoadException` during MEF composition and the `IExtension` part never instantiates. Do not reintroduce Kestrel or `#if NET` branches here. The server exposes these routes on one port:
  - `GET /health` — liveness probe
  - `GET /` — a plain browser GET (no `text/event-stream` Accept) gets a human-readable HTML status page (`HandleStatusPage`), not a 404. MCP clients that GET `/` send `Accept: text/event-stream` and route to the SSE handler instead, so they're unaffected.
  - `POST /` — plain HTTP JSON-RPC (one-shot request/response)
  - `GET /sse` — opens a long-lived `text/event-stream`; first event carries the `/message?sessionId=<id>` URL
  - `POST /message?sessionId=<id>` — accepts JSON-RPC, returns `202 Accepted`, writes the real response back over the SSE stream
  - **Loopback binding registers three prefixes**, not one: `http://localhost:Port/`, `http://127.0.0.1:Port/`, and `http://[::1]:Port/` (see `StartBoundListener` / `BuildLoopbackPrefixSets`). http.sys matches the request Host header against the *exact* registered prefix, so a `localhost`-only prefix made it reject `http://127.0.0.1:Port/` at the kernel level with `HTTP 400 — Invalid Hostname`. All three loopback prefixes bind without admin; only `+`/`*` wildcards need elevation. Binding degrades gracefully (drops `[::1]` if IPv6 is off, then to `localhost`-only). A non-loopback `Host` setting is honored verbatim.
  - Port fallback: tries `Port..Port+19` and logs which one it bound to. Clients should read the resolved port from the log.
  - **The Streamable-HTTP GET stream (`HandleStreamableHttpGet`) flushes its response headers immediately** by writing an initial `: ok` SSE comment before the keep-alive loop. Do NOT enter the ping loop before that first write. The official MCP **Go SDK** (used by Antigravity, Codex) opens this standalone GET stream *synchronously during connect* and blocks on it until the response headers arrive, **before** it sends `notifications/initialized`. If the headers aren't committed until the first ping (one interval later), that GET hangs, the client's connect deadline expires, and the follow-up `notifications/initialized` POST fails with `context deadline exceeded` (the legacy `GET /sse` was never affected because it writes its `endpoint` event immediately). Reproduced empirically against `github.com/modelcontextprotocol/go-sdk`; flushing was the single load-bearing fix. (Claude Code / mark3labs-style clients don't gate the handshake on this GET, so they connected fine even before the fix.)
  - **Each accepted request runs on its own dedicated background `Thread`, not `Task.Run`/the ThreadPool** (see `AcceptLoop`). The SSE / Streamable-HTTP GET handlers block for the entire stream lifetime; on the ThreadPool they tie up workers and, on low-core machines or across handshake retries, starve short requests (the notification POST gets queued but never scheduled → times out, and never even logs server-side). Keep long-lived streams off the pool. The keep-alive loops wait on `cts.Token.WaitHandle.WaitOne(sseKeepAliveMs)` (not `Thread.Sleep`) so server shutdown tears streams down promptly.
  - **`initialize` negotiates `protocolVersion`** (`NegotiateProtocolVersion`): echoes the client's requested version when it's in `supportedProtocolVersions` (`2025-06-18` / `2025-03-26` / `2024-11-05`), else returns the newest. Don't hardcode a single version — the old hardcoded `2024-11-05` violated the MCP lifecycle spec (server MUST echo the requested version if supported). The client's `protocolVersion` arrives in the initialize params as a `JsonElement`.
  - **Unknown JSON-RPC methods get `-32601`** (dispatch throws `MethodNotFoundException`), not the `-32603` internal-error code, and `resources/templates/list` answers an empty list — clients probe it on every connect, and it used to fail and log an error each time. `serverInfo.version` is the assembly's informational version, i.e. the csproj's `McpExtensionVersion`.
  - **An unknown `Mcp-Session-Id` is adopted, not refused** (`TryAcceptStreamableSession`, issue #24). Sessions are in-memory, so a client that keeps its ID across a dnSpy restart presents one this process never issued — and the official TypeScript SDK (Chatbox, among others) doesn't re-initialize on the spec's 404, so it failed every call with "Unknown Mcp-Session-Id" until the user reconnected by hand. A session holds no state here (each POST is answered inline), so POST and the GET stream register such an ID as if we had issued it; only IDs the client ended with DELETE (`terminatedSessions`) still get 404. Don't reintroduce strict rejection. `run-tests.ps1` step [36] covers it.
- **`McpDispatcher.cs`** — transport-independent JSON-RPC handling: method dispatch, `initialize` version negotiation, tools/resources, the error codes, `JsonOptions`, `ServerVersion`. `McpServer.HandleRequest` is a one-line delegate to it; the headless host feeds it stdio lines. Protocol behaviour goes here, never into a transport.
- **`IMcpHost.cs` / `DnSpyMcpHost.cs`** — what the tools need from the process they run in: `GetDocuments` / `OpenDocument`, the `Decompiler`, `InvokeOnUiThread`, and the rename hooks (`ApplyRename` detaches and re-adds the tree node so dnSpy re-sorts it, restores selection and rebuilds open tabs; `RefreshTreeNode` / `RefreshDecompiledViews` for the plain redraws). `DnSpyMcpHost` (MEF-exported) is the only code that touches `IDocumentTreeView` / `IDocumentTabService` / `IDecompilerService`; the headless host implements the same interface with no UI.
- **`headless/`** — `dnSpy.Extension.MCP.Headless.exe`, the stdio host; see "Headless host" below. Excluded from the extension's compile glob (`DefaultItemExcludes`); reaches the extension's internals through `InternalsVisibleTo`.
- **`McpTools.cs` / `McpTools.IL.cs` / `McpTools.Strings.cs` / `McpTools.Xref.cs` / `McpTools.Rename.cs` / `McpTools.RenameSymbol.cs`** — the 32 tools, wrapping `IMcpHost` (loaded-document enumeration and loading — `open_files` calls `host.OpenDocument`, which inside dnSpy is `IDsDocumentService.TryGetOrCreate(DsDocumentInfo.CreateDocument(path))`, the programmatic File → Open — plus the decompiler) and dnlib's `CilBody` (IL view/edit + `ldstr`/operand scan). `McpTools` is a `sealed partial class` split across six files: `McpTools.cs` holds the MEF export, tool schemas, dispatch switch and threading policy, and shared helpers (`GetLoadedModules` / `GetLoadedAssemblies` / `FindAssemblyByName`, `FindTypeInAssembly`, `FindMethod`, cursor codec); `McpTools.IL.cs` holds the IL view/patch/save handlers, the tagged-operand renderer/parser, and the high-level `force_return` / `nop_method` body rewrites (which reuse the same snapshot/revert/save flow via `BuildReturnSequence`); `McpTools.Strings.cs` holds `search_string_literals` / `list_string_constants` (scanning `ldstr` via the shared `EnumerateLdstr` helper) plus `search_constants` (scanning `ldc.i4*`/`ldc.i8`/`ldc.r4`/`ldc.r8` via `EnumerateNumericConstants`); `McpTools.Xref.cs` holds the four cross-reference tools — `find_callers` / `find_references` sweep every method body's operands via the shared `ScanForReferences` helper (matching targets by `ResolveMethodDef`/`ResolveFieldDef`/`ResolveTypeDef` with a FullName fallback for refs into unloaded assemblies); `find_callees` reads ONE method's body and lists its outgoing references (dnSpy Analyze "Uses", deduped per member via `ClassifyOperand`/`CalleeAgg`); `find_overrides` does the virtual / interface polymorphism lookup (dnSpy Analyze "Overridden By" sweeps all subclasses for a class virtual, or all implementors — implicit + explicit, via `ImplementsInterface`/`ImplementsInterfaceMethod` — for an interface method; "Overrides" walks the base chain; signature matching via `SigComparer` + `IsReuseSlot`). The whole-program sweeps run across **all** loaded modules — callers/references/overrides routinely live in a different assembly than the target. `McpTools.RenameSymbol.cs` holds the single `rename_symbol_by_token` entry point plus the type/field/property/event/parameter/generic-parameter handlers; `McpTools.Rename.cs` holds the method-rename core and the value-mapped enum-member batch machinery. List-returning tools use **opaque base64 cursors** (see `EncodeCursor` / `DecodeCursor`) with default page size **10** to stay within AI token budgets. Follow this pattern when adding list tools.
- **Threading: reads run on the HTTP worker, writes on the UI thread, every call serialized.** `ExecuteTool` takes `toolLock`, then runs the handler inline on the HTTP worker thread — unless the tool is in `UiThreadTools` (`open_files`, `patch_method_il`, `force_return`, `nop_method`, `revert_method_il`, `rename_symbol_by_token`, `save_assembly`), which it marshals onto the WPF UI thread via `IMcpHost.InvokeOnUiThread` (the headless host just runs them inline; inside dnSpy this serializes them with AsmEditor's own edits, and letting rename refresh tree nodes/tabs). Consequences:
  - **Read-only handlers must never touch `IDocumentTreeView` nodes** (`GetAllModuleNodes`, `FindNode`, …): they are `DispatcherObject`s and throw "calling thread cannot access this object" off the UI thread. Enumerate through `GetLoadedModules()` / `GetLoadedAssemblies()` / `FindAssemblyByName()`, which read `IMcpHost.GetDocuments()` — inside dnSpy `IDsDocumentService.GetDocuments()`, a lock-protected snapshot, safe on any thread. Decompiling off the UI thread is fine; dnSpy itself decompiles on background threads.
  - **A new tool that mutates metadata or touches the tree/tabs goes in `UiThreadTools`.** Handlers don't marshal or lock themselves.
  - **`toolLock` is only ever acquired on HTTP threads** — writes take it *before* marshaling — so the UI thread never blocks on it. Keep it that way: a reader holding the lock may need the dispatcher synchronously (`McpSettings.Log` does), and a UI thread waiting on the lock would deadlock with it.
  - This replaced running *every* call on the UI thread, which froze dnSpy for the whole length of any long sweep (`find_callers` / `search_string_literals` over a Unity game).
- **`McpProtocol.cs`** — JSON-RPC 2.0 + MCP DTOs. Uses `System.Text.Json` on both TFMs (BCL on net10, NuGet on net48). `McpDispatcher.JsonOptions` writes with `JsonIgnoreCondition.WhenWritingNull` — MCP requires null-stripped payloads.
- **`McpSettings.cs`** — two classes: `McpSettings` (public `ViewModelBase`, the imported service) and `McpSettingsImpl : McpSettings` (the `[Export(typeof(McpSettings))]` impl). The impl persists via `ISettingsService` under a **hardcoded settings GUID** — never change it, or every user's saved settings reset. Property changes drive server start/stop, so toggling "Enable Server" in the UI takes effect without a restart.
- **`McpSettingsPage.cs` / `McpSettingsControl.xaml*`** — WPF settings page wired into dnSpy via `IAppSettingsPageProvider`.
- **`BepInExResources.cs`** — embedded markdown docs served via MCP `resources/list` / `resources/read`. Self-contained, no network.

### Conventions specific to this extension

- **Nested / compiler-generated types are addressable.** `FindTypeInAssembly`, `list_types`, and `search_types` all use dnlib's recursive `ModuleDef.GetTypes()` (not `.Types`, which is top-level only) so async/iterator state machines like `GameOver/<Awake>d__63` are discoverable and resolvable. `FindTypeInAssembly` exact-matches `FullName` first, then retries with separators normalized (`/`, `+`, `.` all collapse) so callers don't have to know dnlib's `/` convention. `list_types`/`search_types` tag each entry with `is_nested` / `is_compiler_generated` / `declaring_type`.
- **`decompile_method` rescues async/iterator bodies.** ILSpy reconstructs state machines at method granularity, but its kickoff pattern-match misses on some compiler output (notably Unity/Mono `async void`), leaving only the kickoff stub. `decompile_method` reads the kickoff's `[AsyncStateMachine]`/`[IteratorStateMachine]` attribute (via `GetStateMachineType`), and if the kickoff output didn't already reconstruct (`await`/`yield` absent), appends the raw `MoveNext` decompilation so the real logic is never lost. `include_state_machine=false` opts out. The state machine's `MoveNext` is also directly decompilable since nested types are addressable.
- **Token-only addressing.** `decompile_by_token` resolves an `MDToken` via `ModuleDefMD.ResolveToken` (scoped to `assembly_name` if given, else swept across all loaded modules and required to be unambiguous) and decompiles the resulting `MethodDef` (or `TypeDef`) through the shared `DecompileMethodToText` helper. This is the escape hatch when a caller has a token from xref / string search but not the declaring type — and the simplest way to reach nested compiler-generated members.
- **`assembly_name` accepts a simple name, a full name, or a file path — and refuses ambiguity.** `FindAssemblyByName` matches a path (anything containing `\` or `/`) against each loaded document's `Filename`, then an exact `FullName`, then the simple name. When a name matches more than one loaded assembly — two copies or versions of one DLL, common when comparing game builds — it throws `ArgumentException` listing every candidate's path instead of taking the first, which used to let a patch, rename or save land on the wrong copy. `list_assemblies` returns each assembly's `Path` for exactly this. Likewise `patch_method_il`'s `method:`/`field:`/`type:` operands resolve in the patched method's own module first (`OperandSearchOrder`), so a same-named copy elsewhere can't turn a self-reference into a cross-assembly MemberRef.
- **List-tool scoping is uniform.** `list_assemblies` (`name_filter`), `search_types` (`assembly_name`), and `list_types`/`search_types`/`get_type_info` (`page_size` via `ResolvePageSize`, `names_only` compact projection) exist to keep responses inside AI token budgets on Unity-sized assemblies. `list_types` also has `base_type` (transitive subclass filter via `InheritsFrom`) and `get_type_info` has `compact` + `members_filter`. Reuse `BuildStringMatcher` (substring or `*` wildcard) for any new name filter so behavior stays consistent.
- **`search_types` + `search_members` together are dnSpy's Ctrl+Shift+K.** `search_types` finds types by name; `search_members` (in `McpTools.cs`) finds methods / fields / properties / events by name across every loaded module (or one via `assembly_name`), optionally filtered by `kinds`. It exists because the xref tools (`find_callers`/`find_references`) require `assembly_name + type_full_name + member_name`, but callers usually only have a bare name from decompiled code and don't know the declaring type — so a name they can't resolve is a symbol they can't analyze. Each `search_members` hit carries `declaring_type` + the raw `MDToken` (`token`), which feed straight into `decompile_by_token` / `find_callers` / `find_references`, closing the search→analyze loop. Property/event accessor methods (`get_X`, `add_X`) also surface under `kind=method`, matching dnSpy. Reuses `BuildStringMatcher`; results are projected once via the `MemberHit` struct so `names_only` and the full row share one scan.
- **Harmony codegen is signature-aware and shared.** `generate_harmony_patch` resolves a real `MethodDef` (via `FindMethod`) and emits a compile-ready `[HarmonyPatch]` class through `BuildHarmonyPatchClass(method, patchType)`: `ref <ret> __result` for a non-void postfix, `<DeclType> __instance` for instance methods, original params by name (positional `__0`/`__1` when names are stripped), and a `new Type[]{...}` disambiguator only when a sibling overload shares the name. `CSharpTypeName(TypeSig)` renders types as compilable C# (primitive keywords, `Outer<Arg>` generics, `T[]`, `Nullable<T>`→`T?`, else fully-qualified with nested `/`→`.`). `generate_bepinex_plugin` reuses `BuildHarmonyPatchClass` for its hooks rather than emitting empty stubs (resolving each hook against `target_assembly`, indenting the class into the namespace, and degrading an unresolved/overloaded hook to a comment) — keep both paths on that one helper so generated code stays consistent. The Harmony conventions match the embedded `bepinex://docs/harmony-patching` resource.
- **MEF everywhere.** New services use `[Export(typeof(T))]` + `[ImportingConstructor]`. Inside dnSpy never `new` up `McpServer`, `McpSettings`, `McpTools`, or `BepInExResources` — let the container wire them. (The headless host has no container, so its `Program` constructs `McpSettings`, `McpTools`, `BepInExResources` and `McpDispatcher` itself.)
- **Tools reach dnSpy only through `IMcpHost`.** Never inject `IDocumentTreeView` / `IDocumentTabService` / `IDecompilerService` into `McpTools`, and don't touch WPF there. A new tool that needs something from dnSpy's UI gets a method on `IMcpHost`, implemented in `DnSpyMcpHost` and, as an inline/no-op equivalent, in `HeadlessMcpHost` — otherwise the headless host can't serve it.
- **Tool errors are results; protocol errors are JSON-RPC errors.** `ExecuteTool` catches every exception a handler throws and returns a `CallToolResult` with `isError: true` and the message — the MCP convention, so the model sees the problem and can retry. Still throw `ArgumentException` with actionable text (a candidate list, the expected format) for bad user input. JSON-RPC error codes come only from `McpServer.HandleRequest`: `MethodNotFoundException` → `-32601`, `ArgumentException` (malformed `tools/call` / `resources/read` params) → `-32602`, anything else → `-32603`.
- **No `#if` TFM branches.** The codebase is currently single-stack (HttpListener + System.Text.Json on both TFMs). The only TFM-conditional item is the `System.Text.Json` `PackageReference` in the csproj under `IsDotNetFramework`.
- **net48 NuGet versions MUST match dnSpy's own resolution.** .NET Framework binds assemblies by *exact* version and dnSpy ships no binding redirect for `System.Text.Json`, so pinning a version dnSpy doesn't ship builds and loads fine and then throws `FileNotFoundException` inside `HandleHttpRequest` on the first MCP request — the server appears up but every call fails ("can't connect to MCP"). This is invisible on net10, which rolls forward, and invisible to the end-to-end suite, which only drives the net10 build. That combination is exactly how issue #21 shipped (we pinned 8.0.5; dnSpy 6.6.0 resolves 9.0.0). dnSpy pulls it in transitively and declares no explicit reference, so there is nothing to inherit — the pin must be updated by hand whenever dnSpy's graph moves. `tests/check-host-deps.ps1` compares both projects' `project.assets.json` and fails on drift; both workflows run it (`build.yml` before the net48 build, `release.yml` before the dnSpy build). Add any new net48-only `PackageReference` to that script's `$guarded` list.
- **`McpSettings.Log` mirrors to disk in Debug builds only.** Under `#if DEBUG` every entry is also appended to `McpSettings.LogFilePath` (hardcoded `D:\dnspy-mcp.log`), which is then the authoritative record — the in-memory `ObservableCollection` is best-effort for the UI and can drop entries when the dispatcher isn't up yet. Release builds, including everything `release.yml` ships, write no disk log at all, so its absence proves nothing; deploy a Debug build to get startup telemetry. On a machine without `D:`, the Debug log goes missing silently unless you change the path.
- **UI-thread marshaling for log.** `Log()` uses `Application.Current.Dispatcher` because `LogMessages` is bound to WPF. Don't bypass it.

### IL editing (list_methods / get_method_il / patch_method_il / force_return / nop_method / revert_method_il / save_assembly)

- **`force_return` / `nop_method` are intent-level rewrites over the same machinery.** `force_return` replaces a body with `load <value>; ret` (value = bool / number / null / `default`, chosen against the method's return `ElementType`; structs only support `default` via a synthesized `ldloca; initobj; ldloc`; void → bare `ret`). `nop_method` == `force_return` with `default`. Both snapshot on first call (so `revert_method_il` undoes them) and persist through `save_assembly`. They throw `ArgumentException` for impossible requests (a concrete value on a void/struct/reference return) before mutating anything.

- **Method identification.** Names alone aren't unique — pass `parameter_types` (array of `FullName`s) or the `method_token` (dnlib `MDToken.Raw`) returned by `list_methods` / `get_type_info`. Token inputs (`method_token`, `token`) accept a decimal uint or a `0x`-prefixed hex string (`ReadOptionalUInt` → `TryParseUInt`), so a token copied straight from dnSpy's UI works unchanged. `FindMethod` throws `ArgumentException` with a candidate-signature list on ambiguity so the AI can retry.
- **Operand grammar is tagged** (`int:`, `str:`, `method:`, `field:`, `type:`, `token:method:|field:|type:`, `label:`, `switch:[…]`, `local:`, `arg:`, `int8:`, `uint8:`, `long:`, `float:`, `double:`). The renderer and parser in `McpTools.IL.cs` share this grammar — keep them symmetric when adding kinds. `InlineSig` / `calli` is unsupported.
- **Edit semantics.** `replace` mutates the existing `Instruction` object in place so branch / switch operands that reference it still resolve correctly. `insert` creates a new `Instruction` and places it before the target index (or appends if index == Count). `delete` removes by reference. All edit indices refer to the pre-batch state — `ResolveEdit` resolves them to `Instruction` references before applying so later inserts/deletes don't shift them.
- **Snapshots preserve identity.** `CilBodySnapshot` captures `(Instruction reference, OpCode, Operand)` per instruction plus the ordered list. `revert_method_il` un-mutates each `Instruction` back to its snapshotted (OpCode, Operand) and re-adds them in order — this is mandatory because a reference-only snapshot would be poisoned by the in-place `replace` mutation. `Instruction[]` switch operands are cloned at snapshot time for the same reason. The store, `ilSnapshots`, is a `ConditionalWeakTable<MethodDef, CilBodySnapshot>` keyed by the `MethodDef` object — never by `MDToken`: tokens are per-module, so with a token key two loaded assemblies' same-token methods (e.g. two copies of Assembly-CSharp) shared one snapshot, and reverting one wrote the other's instructions into it.
- **Save uses `NativeWrite` for `ModuleDefMD`, `Write` for everything else.** Plain `Write` on a module that was loaded from disk drops native stubs, Win32 resources, delay-loaded imports, and mixed-mode metadata; `NativeModuleWriterOptions(md, optimizeImageSize: true)` preserves them. Before writing, memory-mapped I/O is disabled on every `IDsDocument` whose filename matches the target (case-insensitive) via the public `peImage as dnlib.PE.IInternalPEImage` cast — `dnSpy.AsmEditor`'s `IMmapDisabler` is internal so we inline the one-liner. GAC paths are refused via `GacInfo.IsGacPath`.
- **Backup-then-overwrite on same-path saves.** When `output_path` is omitted (or equals the original location), `save_assembly` copies the existing file to `<target>.<yyyyMMdd-HHmmss>.bak` before writing. Side-path saves leave the original untouched and return `backup_path = null`.
- **dnSpy's in-memory tree is NOT refreshed after save.** The `ModuleDef` our patches live in is still the pre-patch one in memory; the user has to reopen the assembly in dnSpy to see saved-to-disk state. This is deliberate — refreshing would require re-composing tabs/nodes under AsmEditor internals we don't reference.
- **No Ctrl+Z integration.** `patch_method_il` does not route through dnSpy's `IUndoCommandService` (it's internal to AsmEditor). Use `revert_method_il` for undo within an MCP session. The snapshot is dropped after revert but survives `save_assembly` (the e2e suite reverts after saving), so reverting in memory and saving again undoes a persisted patch.

### Metadata renaming (`rename_symbol_by_token`)

- **One tool, thirteen `target_kind`s**, all addressed by metadata token: `type`/`class`/`enum`/`interface`/`struct`/`delegate` (TypeDef), `method`, `field`, `property`, `event`, `parameter`, `generic_parameter`, plus `enum_member` and the batch `enum_members`. Every handler validates the token's **table prefix** (`RequireTokenTable`, e.g. `0x02000000` for TypeDef) so a mismatched token fails loudly instead of renaming the wrong row, and rejects the CLR-reserved names (`.ctor`/`.cctor`, an enum's `value__` backing field, the `<Module>` type).
- **Renaming a TypeDef/MemberDef must also rewrite the module's own `TypeRef`/`MemberRef` rows.** Calls into a *closed generic* declaring type (`GenericMethodOwner<int>.Echo`) are encoded as `MemberRef`, not as a direct def operand, so skipping them produces an assembly that saves fine and then fails at runtime. `RenameAnyTypeSymbol` sweeps `module.GetTypeRefs()` with a `TypeEqualityComparer`; the member handlers sweep `EnumerateMethodMemberRefs`/`EnumerateFieldMemberRefs`. The result's `updated_member_references` reports how many rows were touched, and the fixture verifies it by **executing** the renamed members out of the saved DLL.
- **Renames are in-memory and irreversible.** There is no snapshot/revert counterpart to `revert_method_il` — undo means renaming back. Each handler does restore the old names if the mutation throws part-way, so a failure never leaves a half-renamed module.
- **Cross-assembly references are NOT rewritten** — only the target's own module. Another loaded assembly that references the old name keeps referencing it and stops binding once the renamed module is saved. This is inherent to renaming (dnSpy's own AsmEditor behaves the same); the tool description and the result `note` both say so.
- `enum_members` maps names **by constant value**, not by metadata order or current name — the point being that obfuscators scramble names but preserve values, so a caller who knows "value 1 means registered" can push a whole mapping in one call.

### Headless host (`headless/`)

`dnSpy.Extension.MCP.Headless.exe` serves the same tools over the MCP stdio transport (newline-delimited JSON-RPC) with no dnSpy window, so MCP clients launch it on demand. `Program` finds the dnSpy installation it's deployed in (the folder holding `dnSpy.Contracts.DnSpy.dll` + `dnSpy.Decompiler.ILSpy.Core.dll`, or `--dnspy`), installs `AssemblyResolution`, then wires `HeadlessMcpHost` → `McpTools` → `McpDispatcher` → `StdioTransport`.

- **Main must not touch dnSpy / dnlib / extension types.** They only load once `AssemblyResolution.Install` has run (one `AppDomain.AssemblyResolve` handler covers both TFMs: exe dir, dnSpy's bin, `bin\Extensions\dnSpy.Extension.MCP`). That's why everything past setup is in `Run`, marked `NoInlining`, and why `HeadlessOptions` / `AssemblyResolution` are BCL-only.
- **stdout is the protocol channel.** `Main` grabs the raw stdout stream for `StdioTransport` and points `Console.Out` at stderr, so a stray `Console.WriteLine` anywhere can't corrupt it. The log goes to stderr via `McpSettings.Logged` (`--quiet` turns it off).
- **`HeadlessMcpHost` mirrors dnSpy's document service with `UseMemoryMappedIO=false`**: files are read into memory (`new PEImage(bytes, path)`) so the target DLLs aren't locked for the lifetime of the client, then wrapped as the same `DsDotNetDocument` types dnSpy uses, added to the `AssemblyResolver` cache, and `OnAdded()` loads the PDB. The decompiler comes from `dnSpy.Decompiler.ILSpy.Core`'s `IDecompilerProvider`s by reflection, exactly as in `dnSpy.Console.exe`. `InvokeOnUiThread` runs inline; the rename/refresh hooks are no-ops.
- **Deployment mirrors `dnSpy.Console.exe`** (`deploy-headless.ps1`, used by `release.yml` and `run-tests.ps1 -Headless`): the exe goes next to `dnSpy.Console.exe`; net10's DLL goes wherever `dnSpy.Console.dll` is, with AppHostPatcher `-d bin` for build.ps1's `bin\` layout. The runtime configuration is copied from the target bundle — net48 `dnSpy.exe.config` (probing `bin` + the exact binding redirects for the DLLs that bundle ships: the binding environment the extension already runs under in dnSpy), net10 `dnSpy.Console.runtimeconfig.json` (framework-dependent or self-contained exactly as the bundle is). No deps.json is deployed, so the .NET host treats every DLL in the app dir as an app assembly. Only our own exe/DLL ship — never copies of dnSpy's assemblies.
- **The apphost must match the bundle's architecture.** A self-contained bundle's runtime in `bin\` is native, and an x64 apphost can't load the win-x86 bundle's x86 `hostfxr.dll`. `release.yml` builds the apphost per RID (`-r win-x64` / `-r win-x86 --self-contained false`; the DLL is the same AnyCPU build) and `deploy-headless.ps1` refuses a mismatch against `dnSpy.Console.exe`'s PE machine type. Verified against real self-contained x64 and x86 bundles: `COREHOST_TRACE` shows the bundle-local `hostfxr.dll` and "Executing as a self-contained app".
- **Plugin-only installs don't get it.** It needs the per-bundle layout and patching above, which the all-in-one zips provide.

### Test fixture (`tests/fixtures/`)

- **Every change is verified in both modes before it merges**: `run-tests.ps1` (the extension inside dnSpy, over HTTP) and `run-tests.ps1 -Headless` (the stdio host). Both ship, CI runs neither, and a change can pass one and break the other — anything touching `IMcpHost`, `McpDispatcher`, a transport or the deployment scripts in particular. Use `-Tfm net48` as well when a change could differ by runtime (dependencies, binding, reflection).
- `TestIL.cs` + `TestIL.csproj` — a tiny netstandard2.0 assembly covering overloads, constant/string/branch/field/type operands. Checked in; the built `TestIL.dll` is **not** (see `.gitignore`).
- `build-fixture.ps1` — `dotnet build` wrapper that emits `bin/TestIL.dll` and prints its SHA256.
- `run-tests.ps1` — end-to-end driver. Builds the fixture and the extension, deploys the `.x.dll` into dnSpy's Extensions folder, sets `Port=3100` in `%APPDATA%\dnSpy\dnSpy.xml` (because WSL's `wslrelay.exe` commonly holds 3000 even though our `TcpListener` probe reports it free), launches dnSpy with `--dont-load-files` (skips session restore, so the fixture is the only user-loaded assembly) and the fixture as CLI arg, polls `list_assemblies` until `TestIL` appears, then walks through list_methods / decompile_method / get_method_il / patch_method_il / revert_method_il / save_assembly with SHA256 and behavioural asserts (a spawned PowerShell loads the saved DLL and invokes `AddOne(10)` to confirm the +1 → +41 patch took effect on disk). The steps that load duplicate copies of the fixture — `open_files` [32], the ambiguous-name / path-addressing checks [33], and same-token snapshot isolation [34] — run last, because after them the simple name `TestIL` is ambiguous and every tool refuses it; [35] checks the protocol surface (`serverInfo.version`, `resources/templates/list`, `-32601`), and [36] Streamable HTTP session adoption (issue #24). `-Headless` runs the same suite against the headless host over stdio (built, deployed next to `dnSpy.Console.exe` with `headless/deploy-headless.ps1`, fixture preloaded as an argument): every tool call goes through `Send-JsonRpc`, which picks HTTP or stdio, and only the HTTP-specific steps [23] and [36] are skipped; a final check asserts the host exits with code 0 when stdin closes. The host's stderr is drained continuously — an unread pipe would fill and block it.
- The extension csproj sets `<DefaultItemExcludes>$(DefaultItemExcludes);tests/**</DefaultItemExcludes>` so the fixture's generated `AssemblyInfo.cs` doesn't get pulled into the extension build.
